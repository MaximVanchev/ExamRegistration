Темата на проекта е „Приложение на тема по избор“ (вариант 3.1). 2. Теоретична основа

Message Oriented Middleware (MOM) е междинен софтуер, при който приложенията обменят съобщения през посредник (message broker), вместо да се извикват директно. Изпращачът не чака получателя (fire-and-forget), а двете страни не знаят една за друга (loose coupling). Ако получателят временно не работи, съобщенията го чакат в брокера.

Има два основни модела. При point-to-point (опашка, queue) всяко съобщение се обработва от точно един получател, обикновено по реда на пристигане (FIFO). При publish-subscribe (topic) едно съобщение се доставя на всички абонати. Съобщение, което не може да бъде обработено (poison message) или е изтекло, се премества в dead-letter опашка (DLQ), за да не блокира останалите.

Azure Service Bus е облачен брокер на Microsoft, който работи по протокола AMQP 1.0. Предлага опашки, topic-и с абонаменти, потвърждаване на обработката (PeekLock), откриване на дубликати, DLQ и сесии. Azure Service Bus Emulator е официален Docker образ, който предоставя същия AMQP интерфейс локално. Така приложението се разработва и тества без Azure абонамент и без интернет.

Микроуслугите са малки, независимо стартирани и разгръщани услуги, всяка със собствена отговорност. Принципът „smart endpoints and dumb pipes“ означава, че бизнес логиката е в услугите, а комуникационната инфраструктура само пренася съобщенията.

3. Архитектура на системата

Системата се състои от три микроуслуги и общ проект с договорите на съобщенията (фиг. 1). Услугите комуникират единствено чрез Service Bus и не се извикват директно.

Таблица 3. Компоненти на решението
ПроектОтговорност
ExamRegistration.Contractsсъобщения ExamRegistrationRequested и ExamRegistrationProcessed, имена на опашки и topic-и, ServiceBusOptions, каталог с изпити
ExamRegistration.ApiHTTP endpoint-и, валидация на входа, JWT, изпращане в опашката
ExamRegistration.Processorполучаване от опашката, бизнес правила, публикуване на резултата в topic
ExamRegistration.Notifierабонат на topic-а, симулира имейл до студента
ExamRegistration.Api.TestsHTTP тестове на API-то в паметта
ExamRegistration.IntegrationTestsend-to-end тестове срещу емулатора

Последователността при едно записване е следната:

  1. Клиентът изпраща POST /api/registrations с JWT токен.
  2. Api валидира данните, изпраща ExamRegistrationRequested в опашката и връща 202 Accepted.
  3. Processor получава съобщението, проверява правилата и публикува ExamRegistrationProcessed (Accepted или Rejected) в topic-а.
  4. Notifier получава събитието от абонамента notifications и „изпраща имейл“.

    clients.AddClient<ServiceBusSender, ServiceBusClientOptions>((_, _, provider) =>

7. Логика за изпращане на съобщения (D)

Изпращането е капсулирано в класа ServiceBusRegistrationPublisher зад интерфейса IRegistrationPublisher (листинг 4). Интерфейсът позволява в HTTP тестовете да се използва fake реализация.

Листинг 4. Изпращане на заявка в опашката
var sbMessage = new ServiceBusMessage(BinaryData.FromObjectAsJson(message))
{
    MessageId = message.RegistrationId.ToString(),     // откриване на дубликати
    CorrelationId = message.RegistrationId.ToString(), // проследяване
    ContentType = "application/json",
    Subject = nameof(ExamRegistrationRequested)
};
sbMessage.ApplicationProperties["examId"] = message.ExamId;
await _sender.SendMessageAsync(sbMessage, ct);
  • Тялото е JSON, сериализиран от record-а ExamRegistrationRequested, който е общ договор между услугите.
  • MessageId е уникален. При повторно изпращане на същото съобщение брокерът го отхвърля.
  • CorrelationId позволява една заявка да се проследи през всички услуги.
  • ApplicationProperties са метаданни, по които може да се филтрира, без да се чете тялото.

Processor също изпраща съобщения: публикува ExamRegistrationProcessed в topic-а със свойство status със стойност Accepted или Rejected.

8. Логика за получаване на съобщения (E)

Получаването е реализирано в RegistrationProcessorWorker, който е BackgroundService със ServiceBusProcessor (листинг 5).

Листинг 5. Създаване на processor за опашката
_processor = client.CreateProcessor(ServiceBusNames.RegistrationsQueue, new ServiceBusProcessorOptions
{
    AutoCompleteMessages = false,   // ръчно потвърждаване
    MaxConcurrentCalls = 1,         // последователна обработка, коректно броене на местата
    ReceiveMode = ServiceBusReceiveMode.PeekLock
});
_processor.ProcessMessageAsync += HandleMessageAsync;
_processor.ProcessErrorAsync += HandleErrorAsync;

В режим PeekLock съобщението се заключва, но не се изтрива, докато услугата не го потвърди. Така нито една заявка не се губи при срив. Начинът на завършване зависи от резултата (таблица 6).

Таблица 6. Завършване на обработката
СитуацияДействиеЕфект
успешна обработкаCompleteMessageAsyncсъобщението се изтрива от опашката
невалиден JSON (poison)DeadLetterMessageAsyncведнага в DLQ с причина InvalidPayload
временна грешкаAbandonMessageAsyncвръща се в опашката; след 3 опита отива в DLQ

Бизнес правилата са в класа RegistrationValidator. Той проверява дали изпитът съществува, дали срокът не е изтекъл, дали има свободни места и дали студентът вече не е записан. NotificationWorker в Notifier използва същия модел, но за абонамента registration-events/notifications, и за всяко събитие записва в лога симулиран имейл.

9. Authentication и Authorization (F)

Всички механизми работят офлайн, без Azure акаунт и без външен identity provider.

9.1. Автентикация към Service Bus

Услугите се свързват с брокера чрез Shared Access Signature (SAS) connection string (листинг 6). Параметърът UseDevelopmentEmulator=true указва на SDK-то да се свърже с емулатора на localhost.

Листинг 6. Connection string към емулатора
Endpoint=sb://localhost;SharedAccessKeyName=RootManageSharedAccessKey;
SharedAccessKey=SAS_KEY_VALUE;UseDevelopmentEmulator=true;

Стойността се чете от конфигурационната секция ServiceBus чрез Options pattern (листинг 7). Ако connection string-ът липсва, услугата отказва да стартира. Той никога не е в C# кода. Ключът на емулатора е публична стойност, затова е в appsettings.Development.json. За реална среда се подава чрез dotnet user-secrets или чрез променлива на средата ServiceBus__ConnectionString.

Листинг 7. Валидиране на настройките при стартиране
builder.Services.AddOptions<ServiceBusOptions>()
    .Bind(builder.Configuration.GetSection(ServiceBusOptions.SectionName))
    .ValidateDataAnnotations()   // [Required] ConnectionString
    .ValidateOnStart();

9.2. Автентикация на HTTP API

API-то използва JWT Bearer автентикация (AddAuthentication().AddJwtBearer()). Издателят, аудиторията и ключът за подписване се четат от секцията Authentication:Schemes:Bearer. Токените се генерират локално с инструмента dotnet user-jwts, който е част от .NET SDK (листинг 8). Инструментът записва издателя и аудиторията в appsettings.Development.json, а ключа за подписване в user-secrets.

Листинг 8. Генериране на локални токени
dotnet user-jwts create --project src/ExamRegistration.Api --name ivan.petrov \
    --role Student --scope registrations:write -o token
dotnet user-jwts create --project src/ExamRegistration.Api --name admin --role Admin -o token

9.3. Политики за оторизация

Достъпът до endpoint-ите се контролира от две политики (листинг 9). Резултатите при различни токени са дадени в таблица 7.

builder.Services.AddAuthorizationBuilder()
    .AddPolicy(Policies.CanRegister, policy => policy
        .RequireAuthenticatedUser()
        .RequireRole(Roles.Student)

    .AddPolicy(Policies.CanViewAll, policy => policy
        .RequireAuthenticatedUser()

12. Изводи

Реализирана е система от три микроуслуги, които комуникират само чрез Azure Service Bus. Използвани са двата основни модела на MOM: опашка за заявките и topic с абонаменти за резултатите. Приложени са механизмите за надеждна доставка: потвърждаване в режим PeekLock, повторни опити, dead-letter опашка и откриване на дубликати.

Azure Service Bus Emulator позволява цялата система да се разработи и тества офлайн, включително с автоматизирани интеграционни тестове. Преминаването към реален Azure Service Bus изисква само смяна на connection string-а, без промяна на кода.

Възможни разширения: Managed Identity и RBAC вместо SAS при реален Azure; база данни вместо състояние в паметта; сесии (RequiresSession) за подредба на съобщенията по студент; API Gateway пред услугите.
